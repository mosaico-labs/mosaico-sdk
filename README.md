# Mosaico SDK

Draft of the design of the Mosaico SDK.

Parts marked *planned* are designed but not in the code yet: queries, `CancelToken`, the Rust `blocking` module, generic views for ontologies without generated code and the Python ml helpers. Parallel ranges are a possible option, not planned.

## Layers

![SDK layers](docs/diagrams/layers.svg)

- **SDK.** What users import. Python keeps what needs Python: ontology classes and views, exceptions, pandas helpers and, *planned*, ml helpers.
- **API.** The public objects, the same in Python and Rust.
- **Reader and writer.** Internal blocks that run one Flight stream each, or merge several.
- **Connection.** One per client, cloned into every block that calls the server, plus read connections for multi-topic reads, one per window size, and more when the open streams of a connection would go past 1 GiB of windows or 64 streams. Not public in either SDK.
- **mosaicod.** The server. The SDK uses only its six Flight calls.

## Flows

### Topic read

![Topic read](docs/diagrams/topic-read.svg)

1. `topic_handler()` calls `get_flight_info` once and keeps the metadata, and the ticket of a finalized topic with data.
2. A read with no time range reuses that ticket if the topic was finalized at open. A read with a range asks for the ticket of that window first. A topic that had no data at open, or was still being written, keeps no ticket, so each of its reads asks for one again: data written since then is read, and the stream's `msg_count` counts it, but the handler's own metadata (`msg_count`, `timestamp_ns_min/max`, …) keeps the values read at open.
3. The `BatchReader` runs `do_get` and decodes batches in the background.
4. The user gets messages (views), record batches, one Arrow table or one DataFrame.

A topic with no data gives an empty stream. Reads are independent: several can run at once on the same topic. Ranges include the start and exclude the end; either bound can be left out. The core checks the range before any call, with mosaicod's rule: a missing start counts as `i64::MIN`, a missing end as `i64::MAX`, and a range whose start is not before its end raises `InvalidArgumentError`, a `ValueError` (`ErrorKind::InvalidArgument` in Rust). Today's SDK sends it, and wraps mosaicod's refusal in `ConnectionError`. In Python a bound that is not an int64 raises `InvalidArgumentError` before any call. Two limits come from mosaicod: an end at `i64::MAX` reads as no end, and a topic whose first timestamp is `i64::MIN` or whose last is `i64::MAX` reports that bound as `None`.

### Multi-topic read

![Multi-topic read](docs/diagrams/multi-topic-read.svg)

1. `sequence_handler()` calls `get_flight_info` on the sequence once: metadata and one ticket per topic, kept in its topic handlers (the ticket only for finalized topics with data, as for one topic).
2. `get_data_streamer(topics, start, end)` opens one `TopicBatchStreamer` per topic, as `get_batch_streamer` does, all at once. A read with no time range reuses the saved tickets; a read with a range, or a topic that had no data or was still being written at open, asks for a new ticket, in parallel across the topics. A topic with nothing to read opens no stream: one without a ticket, or, in a read with a range, one whose window holds no rows.
3. The `do_get` of the K topics with data run side by side. Their HTTP/2 stream window depends on K and on the latency to the server, measured once per client in the background after connect, so that memory does not grow with K where a small window is enough (see `Connection`).
4. The `MergeReader` merges the K streams by timestamp into windows: the new batches plus the row order. A window ends when a topic has used up its batch, or at 65,536 rows. Equal timestamps follow the topic order.
5. The streamer walks the order and yields `(topic, msg)`: `topic` is the topic's `TopicHandler`, the same object for every row of that topic, and `msg.data` is a view. Python builds the view columns once per batch.

The range is checked once, as for one topic, before any call, also when no topic has data. A topic with no data adds nothing; if no topic has data the stream is empty. Reads are independent as for one topic, and `close()` cascades the same way. An error names the topic it came from and closes every stream of the read.

### Parallel ranges · possible option, not planned

![Parallel ranges](docs/diagrams/parallel-ranges.svg)

The handler would split a time range into N parts and ask for one ticket per part; a `ConcatReader` would read the N streams in parallel and return them in order, so the user gets the same result as a single read. Not built: it multiplies the server work and the client memory of one read, and it helps only when the server has cores to spare. It can come back as an opt-in parameter, off by default.

### Write

![Write](docs/diagrams/write.svg)

1. `sequence_create()` or `sequence_update()` opens a write session with `do_action`.
2. `topic_create()` creates the topic and opens its `BatchWriter` with `do_put`.
3. `push` appends the row to the topic's builder in the core and hands it to the `BatchWriter` at about 1 MiB, or earlier on the flush policy limits. Builders exist for the ontologies written by hand (IMU, Image, CompressedImage). For the other ontologies Python converts the message to one Arrow row, as today's SDK does, and the core buffers the rows with `push_row` under the same rules. A row that alone exceeds the server limit is dropped, notified and counted, and the writer status becomes `RecordTooLarge`.
4. The `BatchWriter` splits batches under the server limit and sends them in the background. The queued data of all topics shares one budget per client: when it is full, the topics send what they have joined so far.
5. Leaving the `with` block (or `complete(result)` in Rust) waits for the sends and finalizes the session. On error, the session policy deletes or reports it. Server errors surface at the next push or when the session finishes.

### Other operations

![Other operations](docs/diagrams/other-operations.svg)

- Sequence lists go through `list_flights`: `list_sequences()` returns the whole list in one call, and `list_sequences_page()` and `iter_sequences()` return it in pages, with the server's cursor, as in today's SDK. Queries, notifications and deletes go through `do_action`. All on the same connection.
- *Planned:* queries are built in each SDK and run by the core.
- *Planned:* reads and queries accept a `CancelToken`: cancelling it stops the call and its streams. Until then `close()` stops them.
- `close()` on the client, a sequence or a topic closes every stream opened below it. A handler stays usable after `close()`. Closing the client is permanent.

## Dependencies

Solid arrows: who creates whom. Dashed arrows: who calls mosaicod through the connection.

![Dependencies](docs/diagrams/dependencies.svg)

- `MosaicoClient` is the only object the user creates directly. It opens the `Connection` and uses it directly for lists, queries, notifications and deletes.
- The client gives handlers, write sessions and, from `query()`, a `QueryResponse`. A `SequenceHandler` also gives its `TopicHandler`s and the `SequenceUpdater`.
- A read returns a streamer. It wraps a `BatchReader` for one topic, or a `MergeReader` for several topics, which drives one topic batch streamer, with its `BatchReader`, per topic.
- A write session owns its `Session` and its topics. `topic_create` registers the topic through the `Session`, then builds its `TopicWriter` and opens its `BatchWriter`, which receives the `push_batch` calls and the rows joined by `push`.
- Every block that calls mosaicod uses a clone of the client's `Connection`. Internal blocks have no public constructor.

## Classes

One name for each concept, in Python and Rust. A member that returns an object by name has no `get_` (`sequence_handler`, `topic_handler`, `topic_writer`); the calls that open a read keep it (`get_data_streamer`, `get_batch_streamer`), as in today's SDK, and so does `msg.get_data()`, which builds a copy. Time bounds are `start_timestamp_ns` and `end_timestamp_ns` in Python (`start`, `end` in the tables); Rust takes one `range`, a `TimestampRange` or a std range over `Timestamp` or `i64` (`..`, `t0..`, `..t1`, `t0..t1`). Names are `sequence_name` and `topic_name`, the ontology class is `ontology_type`. Where a language cannot follow, the names differ on purpose:

- `TopicWriterStatus::Raised` in Rust is `RaisedException` in Python, as in today's SDK.
- `Notification` has `kind` and `created_at` in Rust (`type` is a keyword), `type` and `created_datetime` in Python, as in today's SDK.
- `Message.ontology_tag()` and `ontology_type()` are methods in Python, as in today's SDK, while handlers and writers have them as properties.
- `connect` takes `enable_tls`, `timeout` and `tls_cert_path` in Python, as in today's SDK; Rust has `ConnectOptions` with `tls`, `connect_timeout` and `tls_cert` (PEM bytes, not a path). Both have `read_window_size`, new: the HTTP/2 window of every read stream, in bytes, and `max_streams_per_connection`, new: the most long streams on one connection, 64 by default (see `Connection`).
- `from_env(host, port, timeout)` is a class method of `MosaicoClient` in Python, as in today's SDK; Rust has `ConnectOptions::from_env(host, port)`, which reads the same variables into the options given to `connect`.
- `max_batch_size_bytes` is a property of the client in Python, as in today's SDK, and `info().max_batch_size_bytes()` in Rust.
- `serialization_format` is today's `SerializationFormat` enum in Python and `Result<Format>` in Rust, with the `Format` type that `Encode::FORMAT` already uses.
- The owned copy of a message is `msg.get_data()` in Python and `msg.to_model()` in Rust, where the model and the view are different types.
- Times are a `Timestamp` in Rust (nanoseconds since the epoch, in an `i64`): time bounds, created and completed times, `msg.timestamp_ns` and the timestamp of `push`. Python has plain ints, with the same names. Arrow `timestamp_ns` columns stay Int64 in both.
- User metadata is a dict in Python, `{}` when there is none. Rust has `user_metadata()`, which returns `Result<Option<&UserMetadata>>`, `user_metadata_as::<T>()` for a serde type and `user_metadata_json()` for the stored text.
- `list_sequences_page` takes `cursor=` (bytes) or `order_by=` in Python. Rust takes a `PageStart`, made from a `SequenceOrder` or a `SequenceCursor`, so it cannot get both; its limit is a `u32`.
- `iter_sequences` is a generator in Python and a `SequenceNames` with an async `next()` in Rust.

### Python SDK · public

The Python package, rebuilt on the Rust core through PyO3. Calls are synchronous, release the GIL while waiting and stop on Ctrl+C. A read whose next batch or window has already arrived returns without releasing it; pyarrow still releases it while importing each batch. When another Python thread holds the GIL, getting it back after that import costs up to Python's switch interval for every batch. So `get_data_streamer`, on a topic or a sequence, times each import: after three slow imports in a row (1 ms or more each) the stream starts reading ahead in a background task, up to 8 MiB per stream, and hands Python everything already arrived as one batch or window, up to 8 MiB. Fewer imports, fewer handoffs. A stream that is never slowed this way keeps reading one batch at a time and costs nothing more. Rows and their order do not change. `get_batch_streamer`, `to_arrow` and `to_pandas` are left as they are.

Ctrl+C and other signals run their Python handlers while a call waits, and since Python 3.12 so can the finalizers of the garbage collector. If that code calls the same write session (its `SequenceWriter` or any of its `TopicWriter`s) or the same stream as the waiting call, the call raises `MosaicoError`: the waiting call holds the locks of that session or stream and goes on only after the handler returns, so the second call would wait for ever. Calls on other sessions, other streams and the client work as usual. Today's SDK has no locks, so such a call works there. The Arrow C stream of a streamer looks for signals only on the main thread, where Python runs its handlers. A handler that raises ends the read with pyarrow's error (`interrupted by TimeoutError`); a `KeyboardInterrupt` comes back as itself, and any other exception is raised again at the next Python call after that error, so `sys.exit()` in a handler still exits and an `except Exception` does not swallow it. An `except` right around the read sees pyarrow's error first. Both come back where Python next checks for signals: if the read sits directly in a `with` block, that can be the start of its `__exit__`, which then does not run (a write session left this way stays open on the server and is logged when it is garbage-collected). Today's SDK raises the handler's exception from the read.

| Member | What it does |
|---|---|
| `msg.data` | Read-only view of one row, generated in Python. A field is read only when accessed. Rust has the same field: `msg.data` is a typed view. Differences from today's SDK, where `data` is the pydantic object: a view prints its fields (binary fields as their length, without copying them) but has no `==`, so compare `msg.get_data()`. Reading a binary field copies its bytes; the last bytes read in a batch are kept, so reading `.data` again, or `get_data()` after it, gives the same `bytes` object, as today's SDK does. A nested struct stored valid but with all its fields null is a view whose optional fields are `None` and whose required fields raise `SchemaError`; `get_data()` gives the empty object for it (`Header()`) or raises `SchemaError`, where today's SDK gives `None` |
| `msg.data` (type without generated code) | *Planned*: a generic view built at runtime from the topic schema, with the same access and no static types. Today Python and Rust read messages for `IMU`, `Image` and `CompressedImage`, with views written by hand. In Python, `get_data_streamer` on another ontology raises `NotImplementedError`: on a topic it points to `get_batch_streamer()` and `to_arrow()`, on a sequence it lists the topics without views |
| `msg.get_data()` | Owned ontology object, a copy of the row. Python converts the model's fields of a whole batch to Python values once, then validates each row with the model's own pydantic validator; binary fields are read per row. If the previous batch of the stream used `get_data()` on fewer than one row in four, the batch is read field by field instead, and the whole-batch conversion starts once one row in four has been asked for. Columns the model does not have are skipped. A row that fails validation is built again field by field, so the errors are the same as reading the view (`SchemaError` for a null required field). `get_data(target_type)` returns `None` when the message is of another type, as in today's SDK |
| `to_pandas(start, end)` | One DataFrame with dotted column names |
| `MosaicoError` | Base class of every exception the SDK raises. Subclasses by cause: `ConnectError` (also a `ConnectionError`), `SequenceNotFoundError` (also from a write session whose sequence or session is gone), `TopicNotFoundError`, `InvalidArgumentError`, `SchemaError` and `StreamClosedError` (also `ValueError`), `AlreadyExistsError`, `PermissionDeniedError` (missing or wrong API key, also a `PermissionError`), `OntologyMismatchError`, `StreamError`, and `ServerError` for the rest |
| `image_from_linear_pixels(data, stride, height, width, encoding)` | Same signature as today's SDK; PNG is encoded in Rust without the GIL, same layout (8-bit gray, height × stride). A size mismatch raises instead of falling back to RAW |
| `encode_png(data, height, stride)` · `encode_png_batch(batch)` | PNG of one buffer, or of every `raw` row of an `Image` batch on all cores, for `push_batch` |
| `decode_png(data)` · `decode_png_batch(batch)` · `decode_png_table(table)` | Back to the raw bytes, as `to_linear_pixels` of today's SDK but returning `bytes`. The batch and table forms decode every `png` row and mark it `raw`; the table form decodes all its rows on all cores (the server sends images a row or two per batch). Every PNG type gives the same bytes as Pillow, which today's SDK uses (low bit depths expanded to one byte per pixel, 16-bit color to 8 bits). An invalid PNG raises instead of returning the data unchanged. `MOSAICO_PNG_THREADS` limits the threads of encoding and decoding |

### Rust SDK · public

The core crate itself, used directly by Rust programs. Async on tokio; a blocking module that mirrors the same API is planned. Errors are `Result<T, Error>` with an error kind. Generated ontology types read rows as typed views.

| Member | What it does |
|---|---|

| `#[non_exhaustive]` | One rule for the public types, so later additions do not break callers. What the SDK returns (`Notification`, `ServerInfo`, `SemVerItem`, `ServerConfig`, `SessionInfo`, `Message`, `SequencePage`, `MergeWindow`, `WindowBatch`) cannot be built outside the crate. Enums that may grow (`ErrorKind`, `TopicWriterStatus`, `Compression`, `Format`, `SequenceOrder`, the two error policies) need a `_` arm in a `match` |
| `topic.get_data_streamer::<Imu>(range)` | Typed read. The type must match the topic ontology tag exactly. `..` reads everything, `t0..t1` a window |
| `Timestamp` · `TimestampRange` | A time in nanoseconds since the epoch, made from an `i64` (`Timestamp::from_ns`, `From<i64>`) or a `SystemTime` (`try_from`, refused outside the `i64` range), read back with `as_ns()`; no arithmetic. | `UserMetadata` | The user metadata of a sequence or topic: a JSON object (a serde_json `Map`) whose keys are checked as mosaicod checks them, at every way of building it: `from_json`, `from_serialize` (any serde type), `insert`, `TryFrom` a `Map` or `Value`, and serde `Deserialize`. | `blocking::MosaicoClient` | *Planned.* The same API without async |
| `Error::kind()` | Connection, not found, invalid argument, schema, closed, server, … |
| `RecordBatch` | arrow-rs batches, passed without conversion |

| `trait Encode` · `RecordBuilder` | Write side of an ontology: `FORMAT`, payload `fields()`, `size()` of a row and a builder that appends rows to Arrow columns. Written by hand for `Imu`, `Image`, `CompressedImage` |
| `seq.topic_create_for::<Imu>(name, metadata, on_error)` · `topic.push(ts, &imu)` | Typed write: the topic schema comes from the type, rows go through the builder. `metadata` is an `Option<&UserMetadata>`, `ts` a `Timestamp` or an `i64`. `push` refuses a type whose tag or format differs from the topic's (invalid argument), as Python does |
| `topic.push_row(row)` | One record already in Arrow (one row with the topic schema), for schemas with no `Encode` type: buffered and sent like typed records, where `push_batch` would queue every one-row batch on its own. The core estimates its size from the Arrow buffers, as for splitting batches, and view columns (`Utf8View`, `BinaryView`, as mosaicod sends them) count the bytes they point to; a row whose encoded form still exceeds the limit is dropped at encoding. ### MosaicoClient · public

Entry point. Holds the main connection, plus read connections (see Connection), and reads the server version and limits once, at connect. Creates handlers and write sessions. Catalog operations and queries go straight to the connection.

| Member | What it does |
|---|---|
| `connect(host, port, timeout, enable_tls, compression, tls_cert_path, api_key)` | Rust: `connect(ConnectOptions::new(host, port))`, the rest set with its methods. Opens the connection and calls `info`. Python also takes today's `GRPCCompression`: its `level` is ignored, and `StreamGzip` gives no compression, with a warning. Today's SDK behaves the same, because its gRPC ignores the level on the client and no longer knows `StreamGzip`. `gzip` is applied by gRPC on the I/O threads (two in Python), a whole message at a time, in both directions; `lz4` and `zstd` compress the Arrow buffers while encoding, off those threads, so they suit heavy writes better |
| `from_env(host, port, timeout=5)` | `connect` with the settings of the environment, as in today's SDK: `MOSAICO_TLS_CERT_FILE`, when set, is the `tls_cert_path` and turns TLS on; `MOSAICO_API_KEY` is the API key (empty means none). Without them it is a plain `connect`. An empty certificate variable raises `InvalidArgumentError`, a missing file `FileNotFoundError`, as `connect` does with the path. Rust: `ConnectOptions::from_env(host, port)?`, which reads the certificate file and gives `ErrorKind::InvalidArgument` if it cannot |
| `info()` | The server's `ServerInfo`, read once at connect, so the call sends no request: `version`, `semver` (`major`, `minor`, `patch`, `pre`, `None` when empty) and `config` (`grpc_max_decode_message_size`, `grpc_max_encode_message_size`, `grpc_target_encode_message_size`). In Python it is today's `ServerInfo` dataclass, so it compares equal to the one of today's SDK |
| `max_batch_size_bytes` | The largest batch the client sends, 10 % below the server's decode limit: the same value as today's SDK |
| `sequence_handler(name)` | `SequenceHandler`. Raises if the sequence does not exist |
| `topic_handler(sequence_name, topic_name, ontology_type=…)` | `TopicHandler`, checked against the ontology before any call. Rust takes no ontology: the type goes on `get_data_streamer::<T>()` |
| `sequence_create(name, metadata)` · `sequence_update(name)` | A write session, used in a `with` block. A new name is checked as in today's SDK, at the call: letters, digits, `-` and `_`, starting with a letter or a digit; otherwise `InvalidArgumentError`. The metadata keys are checked as mosaicod checks them, in nested objects and in arrays too: not empty, no `--`, only ASCII letters, digits, spaces, `_` and `-`. A bad key raises `InvalidArgumentError` with its path at the call, before the `with` block and before any request, and so does a float that JSON cannot hold (NaN, infinity), without the path; today's SDK gets mosaicod's refusal after the call. `None` means no metadata. In Rust the `UserMetadata` is checked when it is built |
| `list_sequences()` · `sequence_delete(name)` · `session_delete(locator)` | `list_sequences` returns every name in one call through `list_flights`, ordered by creation; deletes go through `do_action` |
| `list_sequences_page(limit=50, cursor=None, order_by=None)` · `iter_sequences(page_size=50, order_by=SequenceOrder.CreatedAt)` | As in today's SDK, with its `SequencePage` (`names`, `next_cursor`) and `SequenceOrder` (`CreatedAt`, `Name`). A page starts from an order (by creation when neither is given) or from the `next_cursor` of the previous page, which carries its order. `limit=0` returns everything left. `next_cursor` is `None` on the last page; a page that is exactly full still has a cursor, and the next page is empty. Pages are read live: by creation they pick up sequences created later, by name only new names after the cursor. Cursors work in both SDKs. `iter_sequences` yields the names, asking for the next page only when it needs it. A limit that is negative, above `u32` or not an int, a cursor with `order_by` and an invalid cursor raise `InvalidArgumentError`, a `ValueError`. Today's SDK raises `ValueError` for a negative or too large limit and for a cursor with `order_by`, `TypeError` for a limit that is not an int, a protobuf `DecodeError` for cursor bytes it cannot decode, and the server's refusal for an empty cursor. The cursor is bytes or any bytes-like object (`bytearray`, `memoryview`), as in today's SDK; anything else raises `TypeError`. Rust: `list_sequences_page(limit, SequenceOrder::Name)`, then `list_sequences_page(limit, &cursor)`; `iter_sequences(page_size, order_by)` gives a `SequenceNames`, whose `next()` after an error asks for the same page again |
| `sequence_exists(name)` · `topic_exists(sequence, topic)` | `False` when the server answers not found or rejects the name as invalid; other errors raise |
| `list_*_notifications(…)` · `clear_*_notifications(…)` | Notifications of a sequence or topic, such as dropped records or a failed session. Each one has `sequence_name`, `topic_name`, the type, `message` and the creation time |
| `query(…)` | *Planned.* Runs a query. Results grouped by sequence |
| `close()` | Closes every stream of the client and its handlers, and ends every call still waiting for the server, also in other threads, with a closed error. A call cut this way may already have been applied by the server, so a write session it leaves behind is reported as one that may stay open; a sequence created by `sequence_create` whose session could not open, and could not be deleted again, is reported the same way. Permanent: later calls fail as closed. A write session still open stops its uploads and can no longer finalize or delete itself, so it stays open on the server, as its error says |

### TopicHandler · public

One topic. Opening it reads the metadata once: ontology tag, time range, counts, user metadata and ticket. The Arrow schema arrives at the start of each read.

| Member | What it does |
|---|---|
| `name` · `sequence_name` · `ontology_tag` · `timestamp_ns_min` · `timestamp_ns_max` | Metadata read at open. Python also has `ontology_type`, the class given at open. In Python `str()` is the name and `repr()` shows sequence, name and type |
| `created_timestamp` · `completed_timestamp` · `locked` · `serialization_format` · `chunks_number` · `total_size_bytes` · `msg_count` | The rest of the metadata of `get_flight_info`, with no other call: a snapshot taken at open, also for the topics of a `SequenceHandler`, so a topic still being written keeps the values it had then (open the handler again, or take it again after `reload()` on its sequence, to see new ones). ### SequenceWriter · SequenceUpdater · public

A write session: a new sequence (`sequence_create`) or new topics in an existing one (`sequence_update`). Same API; they differ only in how they open. ### MergeReader · internal

The k-way merge of a multi-topic read. Drives K topic batch streamers, each with its `BatchReader`, and keeps one head per topic in a heap on `(timestamp, topic index)`, so equal timestamps follow the topic order. A window holds the batches loaded since the previous window and the order of its rows as topic indexes; it ends when a topic has used up its batch, so every row of a window points into a batch the caller already has, or at 65,536 rows. ### BatchWriter · internal

One `do_put` per topic, open from `topic_create` until the topic closes, on a connection with a free stream (see `Connection`): HTTP/2 carries the uploads of many topics side by side. Today's SDK puts all of them on one connection. Receives the batches of `push_batch` and the rows joined by `push`, and knows no ontology type. Converts view columns (`Utf8View`, `BinaryView`) to plain ones, splits batches over the server limit read at connect, joins small ones up to it (at most 4,096 batches in one message), and sends them in the background from a queue bounded in bytes, about four messages at the server limit, and by the client's write budget. Each queued batch counts its Arrow buffers plus a fixed cost per batch and per column, so many tiny batches cannot hold more memory than the bound. A message is sent as soon as that count reaches the server limit, even when its rows take less, so pieces waiting to be joined never fill the queue. The budget is shared by all the topics of a client: 512 MiB, or four messages at the server limit if that is larger. A message stays counted until it has left the connection: its share is released when two newer messages of the topic have been handed to gRPC, at the end of the stream, or when the budget is full and the topic has nothing else to send. Not counted: a batch while it is being encoded, as raw and encoded copy side by side (at most one message per topic). When the budget is full, every topic sends what it has joined so far instead of waiting to fill a message; below it nothing changes. A single row over the limit is dropped and reported as a row dropped at the push is: status and notifications belong to the topic's reporter, which the `BatchWriter` shares with its `TopicWriter`. Local errors are raised at once; server errors at the next push or at finish.

| Member | What it does |
|---|---|
| `enqueue(batch)` · `drain()` | Queues a batch, waiting for room in the queue and the budget. A call cancelled after its first piece is queued keeps the rest, which `drain` sends before anything new |
| `flush()` | Sends the joined batches now |
| `finish()` | Ends the `do_put` cleanly, so the server finalizes the topic, and reports the first error |
| drop | Without `finish()`, or with `finish()` dropped before it ends, cancels the `do_put`: the topic is not finalized |

### Connection · internal

One main gRPC connection per client, for actions and the other short calls, and for reads and uploads while it has room, plus the connections described below: the six Flight calls, TLS, the API key header and gzip, in both directions. Reads version and limits with `info` at connect, maps errors to categories and holds the client's write budget.

Every connection sends an HTTP/2 keepalive ping every 30 seconds, also while it has no stream open, and drops the connection if the ping gets no answer within 60 seconds; the next call opens a new one. The answer can queue behind a 16 MiB frame already on its way, so the timeout leaves room for a slow link. A client left idle, or a read connection kept between multi-topic reads, thus stays open through proxies and NAT that close silent connections, and a dead one is found before the next call waits on it.

The HTTP/2 stream window, 16 MiB, is a setting of the whole connection. A multi-topic read of K topics uses a window of 16 MiB / K, rounded down to a power of two, but not below a minimum set by the round-trip time (RTT) to the server: 2 MiB below 2 ms, 8 MiB below 10 ms, otherwise 16 MiB. A stream cannot move more than its window per round trip, so a small window is enough only near the server. The RTT is the fastest of five `info` calls sent one after the other in the background right after connect, so `connect` does not wait for them; a multi-topic read that starts before they answer waits for them. A call that fails is skipped; the five together stop at the connect timeout. If none answers, the minimum is 8 MiB. A window below 16 MiB runs on a read connection with that window, opened at the first read that needs it, one per size (8, 4 or 2 MiB, or smaller for reads of many topics), more when one is full, and shared by every clone of the client, with the same TLS, API key, compression and limits. The window is set by the topics that have rows to read. The windows of one read add up to at most 1 GiB, half of the connection window, so with many topics the window goes below the RTT minimum (above 64 topics at 16 MiB, above 512 at 2 MiB): a stream nobody is reading keeps its window full, and if those streams filled the connection window the stream the reader waits for could not move, nor any other call on that connection. The same bound holds for each connection across reads: every connection counts the windows of its open streams, and a read that would take them past 1 GiB opens another connection with the same window, for example the 65th open stream of single-topic reads, or a second 64-topic merge. A read of one topic and a read at 16 MiB use the main connection while it has room, and every other call stays there. Closing the client drops the read connections.

`read_window_size`, between 64 KiB and 1 GiB, replaces all of the above with one window for every read stream, of one topic or of a merge, and the RTT is not measured. A merge whose streams would go past 1 GiB uses 1 GiB / K, rounded down to a power of two. A small window keeps memory down, at the price of speed far from the server; a large one does the opposite.

A server or proxy can limit the streams open at once on one connection (HTTP/2 `SETTINGS_MAX_CONCURRENT_STREAMS`). mosaicod sets no limit, but proxies do: 100 in HAProxy, 128 in nginx, 250 in Traefik. Past the limit a new stream does not fail: it waits for a free slot, and every later call on that connection, short ones too, waits behind it. A slot frees only when a stream ends, and the streams that hold them are uploads and reads the same code would close next, so the client would hang with no error, for example at the 129th `topic_create` behind nginx. Today's SDK would hang too: it sends everything on one connection. So every connection also counts its long streams, the `do_put` of each open topic and the `do_get` of each read, and allows at most 64 of them, below the lowest of these limits. The next one goes to another connection with room, opened if none has, and never waits for a slot. A merge of more topics is split across connections, 64 topics each. Short calls are not counted; on the main connection they use the slots above 64, wait at most for one another, and end. A slot is given back when the reader or the upload is dropped. `max_streams_per_connection` lowers the count for a proxy set below 100: leave a few slots for short calls. A limit lowered while the connection is open, or a limit for the whole proxy (connections or requests), is not covered; the proxy then refuses with an error instead of hanging.

The HTTP/2 adaptive window of hyper is not used: it makes the window of the whole connection adaptive too, and a merge stalls when the streams it is not reading fill it.

| Member | What it does |
|---|---|
| `connect(options)` | Opens the channel |
| `readers(k)` | The connections for the `do_get` of a read of k topics, one per group of at most 64, each with a lease of its windows and streams held until each stream ends: the main one for one topic or at 16 MiB while it has room, otherwise a connection of that window with room, opened if none has. Waits for the RTT measured after connect when k ≥ 2, unless `read_window_size` is set |
| `writer()` | The connection for the `do_put` of one topic, with a lease of one stream held until the upload ends: the first connection with room, the main one first, otherwise a new one |
| `info()` | Server version and message size limits |
| `get_flight_info(descriptor)` | Metadata and tickets |
| `get_schema(descriptor)` | The stored Arrow schema of a topic, for `ontology_schema` |
| `do_get(ticket)` · `do_put(descriptor)` | Batch streams |
| `list_flights(criteria)` | Sequence names, in one response: a limit and either an order or the cursor of the previous page. Each name comes with its cursor, and the last one starts the next page |
| `do_action(name, body)` | Every other operation |

Every call ends with a closed error when the client is closed, also while it waits for the server: a call stuck on a server that never answers (a lock held in the database, a proxy that lost the request) would otherwise block its thread for good, since keepalive pings are still answered.
